# Оптимизация памяти (дополнение к `SKILL.md`)

Читается по требованию, а не каждую сессию: блок нужен раз в неделю,
а `SKILL.md` грузится в каждой сессии у каждого участника.

## Триггер

Оптимизация запускается:

- по команде пользователя;
- автоматически только в режиме анализа, если пришло время по конфигу.

⚠️🔴 **Просрочка — не повод ждать, пока соседние сессии закончатся.** В живой памяти их почти
всегда несколько и живут они часами ⟹ «сделаем, когда никого не будет» на практике означает
«не сделаем никогда» (замер 21.08: оптимизация просрочена на 8 дней при десяти активных
сессиях подряд). ⟹ Оптимизацию делят **не по времени, а по радиусу записи**: большая её часть
безопасна при любом числе соседей, а ждать тишины должна только меньшая.

## 🔑 Радиус записи: три класса операций

Опасна не «оптимизация», а конкретная запись — и то лишь та, что переписывает файл, в который
пишет кто-то ещё. Каждый пункт анализа сразу помечай классом; дальше класс решает всё.

| класс | что это | когда можно |
| ----- | ------- | ----------- |
| **A. свой файл на объект** | `task.md` и артефакты в папке задачи, `tmp/<slug>/`, новый топик, свой файл дня | **всегда**: две сессии физически не пишут в один файл |
| **B. общий файл, точечная правка** | снять один устаревший факт в `MEMORY.md`, дописать раздел в конец топика, поправить фронтматтер | **всегда**, но только `Edit`/append, с `pull --rebase` перед и коммитом сразу после |
| **C. переписывание или перемещение целиком** | сжатие `MEMORY.md`, склейка дневников, перенос топика между банками, расщепление топика, массовое переименование | **только когда соседей нет** — проверить фактом непосредственно перед началом |

⚠️🔴 **Чем класс C отличается по существу:** чужая запись, появившаяся между твоим чтением и
твоей записью, исчезает молча, и самопроверка «мой текст на месте» этого НЕ ловит — свои
строки как раз сохраняются. Постфактум это видно только как коммит соседа с большим числом
удалённых строк.

## Проверка «соседей нет» — перед каждым блоком класса C

Доска, прочитанная при старте, к моменту оптимизации протухла: соседняя сессия могла начаться
три часа назад. Перечитывать так — часть 2 побочных действий не делает (их делает только часть 1),
поэтому проверка ничего не двигает:

```bash
python <навык>/scripts/yamem-start.py --memory <путь> --sid <свой sid> --part 2 --no-sync
```

Есть активные (🔵) кроме себя — класс C отложить. Плюс дешёвая проверка по конкретному файлу:
`git log --since='2 hours ago' --oneline -- <файл>` — если сосед в него уже коммитил, тема живая
и переписывать её целиком нельзя, даже когда доска выглядит пустой.

## Фаза 1 — Анализ (без изменений в файлах)

Ничего не меняй в файлах. ⭐ **Анализ безопасен при любом числе соседей** — он не пишет ⟹ гонять
его можно всегда, даже если выполнение придётся отложить целиком.

Проверь (в скобках — класс будущей правки):

- ⚙️ **временный каталог проекта** (`tmp/` в корне) — **(A)**: сначала **вылови ценное и переложи**,
  и только потом чисти. 🎯 Мимо памяти регулярно оседают именно там: боевой скрипт или systemd-юнит
  (место — `ops/`), артефакт задачи (место — папка задачи), справочный материал (место — `docs/`).
  ⚠️ Файл во временном каталоге выглядит мусором и сносится не глядя — так едва не потерялся
  единственный экземпляр рабочего сервиса. После разбора — снести всё, что **неактивно больше недели** (порог по `mtime`).
  🔑 Короткий порог безопасен только в паре с правилом **«сослался на файл — вынеси его из временного каталога тем же заходом»**: без него уборка убивает ссылку вместе с файлом.
  ⟹ перед сносом проверить, не упоминается ли объект в топиках и задачах — грепом по имени,
  а не на глаз.
  ⚠️ Соседняя сессия держит там свои рабочие файлы: отбирать **по mtime** и не трогать каталог,
  чьё имя совпадает с темой активной сессии на доске;
- **дневники** — **(C)**: склейка файлов одного дня в один. ⚠️🔴 **Сегодняшний день не склеивать
  никогда** — файлы `YYYY-MM-DD.<sid>.md` активных сессий ещё пишутся. Безопасны только дни
  старше `diary_read_days`: их уже не читает стартер, и ссылки на них не двигаются под ногами;
- **задачи без движения** (давний `updated` при статусе, отличном от `done`) — **(A)**;
- разросшиеся `task.md` — признак, что в задачу пишут хронику вместо `journal.md` — **(A)**;
- папки задач, из которых ещё не извлечено знание в топики — **(A/B)**;
- устаревшие факты в `MEMORY.md` — **(B)**, если снимаем точечно; **(C)**, если это сжатие раздела;
- дубли или пересечения между топиками разных банков — **(C)**;
- топики без «Дата актуализации» там, где содержание зависит от чужих версий и статусов — **(B)**;
- ⚠️ **расползание одной темы**: универсальные куски осели в топике `local`, хотя одноимённый
  топик в общем банке уже есть — **(C)**, кандидат не на удаление, а на перенос куска туда.

Консервативные правила:

- ⚠️ **одноимённые топики в разных банках — это НЕ дубль, а штатная пара** «универсальное + дельта»;
  сливать их в один банк нельзя;
- не считай топик `local` дублем, если в нём есть проектная специфика;
- не предлагай удалять папки задач, если из них ещё не извлечены знания;
- **задачу без движения не удаляют и не гадают, а разбирают по одному правилу:** `done` — только
  если выполнен **её собственный критерий готовности** (соблазн закрыть «в целом сделанное» силён
  и стоит ровно той части, ради которой задачу заводили); `waiting` — если ждём **чужого**
  следующего действия, и рядом пишут, чьего именно; иначе `new` — «работа наша, её просто никто
  не ведёт». 🔑 Граница `waiting`/`new` — **не срок лёжки, а чьё следующее действие**; без неё всё
  протухшее сваливается в одну кучу и разбор приходится делать заново через месяц;
- ⭐ **закрываешь задачу с живым хвостом — переселяй хвост отдельной задачей, а не проглатывай:**
  вместе со статусом `done` иначе исчезает работа, которую больше никто не увидит;
- любые удаления и переносы считай потенциально рискованными.

## Фаза 2 — Отчёт

Покажи пользователю краткую сводку — **двумя списками, по радиусу записи**:

- **можно сделать сейчас (A и B)**: что архивировать, что удалить, что перенести в топики и в
  какой банк, какие факты выглядят устаревшими;
- **требует тишины (C)**: то же самое, но с пометкой, чего ждём — момента, когда на доске нет
  активных соседей.

Жди подтверждения. До подтверждения не меняй файлы. 🎯 Смысл деления: одобряют не «оптимизацию»
вообще, а конкретные действия ⟹ безопасная часть уходит в дело сегодня, а не откладывается
за компанию с рискованной.

## Фаза 3 — Выполнение (после одобрения)

После подтверждения пользователя:

- выполни только явно одобренные изменения, **в порядке A → B → C**, и коммить каждый блок
  отдельно: чем короче окно между чтением и коммитом, тем меньше шанс разойтись с соседом;
- перед блоком C — перечитать доску (рецепт выше) и сделать `git pull --rebase`;
- **после блока C проверь, что чужое не пропало**: `git show --stat HEAD`, и если удалённых строк
  много — `git show HEAD -- <файл>` глазами. Пропавшее возвращают **слиянием**
  (`git show <прошлый коммит>:<путь>` даёт прежнюю версию), а не перезаписью поверх;
- обнови `Последняя оптимизация: YYYY-MM-DD` в `MEMORY.md`;
- ⚙️ пересобери представления `backlog.md`/`archive.md` — **после** `git pull --rebase`;
- при необходимости зафиксируй изменения по git-правилам выше.
