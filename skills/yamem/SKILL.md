# Память проекта (yamem)

## Конфигурация

Конфиг: `.agents/memory/yamem.config.yaml`.

Если файла нет, используй значения по умолчанию:

- `banks` = один банк `local` в `banks/local`
- `commit_on_update=false`
- `optimization.auto=true`
- `optimization.interval_days=7`
- `diary_read_days=7`

Если не указано иное, все пути ниже относительны к `.agents/memory/`.

## Структура памяти

```text
.agents/memory/
├── yamem.config.yaml
├── MEMORY.md                        # устойчивые факты, ограничения и правила
├── README.md                        # как устроена эта память
├── backlog.md                       # ⚙️ ГЕНЕРИРУЕТСЯ из задач — руками не править
├── archive.md                       # ⚙️ ГЕНЕРИРУЕТСЯ из задач — руками не править
├── diary/
│   └── YYYY-MM/                     # по месяцам, иначе каталог растёт без предела
│       └── YYYY-MM-DD.<sid>.md      # <sid> — короткий id сессии, см. «Параллельные сессии»
├── .sessions/
│   └── <sid>.md                     # доска активных сессий: кто сейчас в работе и над чем
├── tasks/
│   └── YYYY-MM/                     # месяц ЗАВЕДЕНИЯ задачи (`created`)
│       └── <slug>/                  # одна задача = одна папка, имя без даты
│           ├── task.md              # 🔑 сама задача: фронтматтер + что сделать + критерий готовности
│           ├── journal.md           # ход работ по этой задаче (по желанию)
│           └── ...                  # артефакты задачи: plan.md, report.md, выгрузки, скрипты
└── banks/
    ├── local/                       # свои топики — есть в любой установке
    │   ├── README.md
    │   └── topics/<topic>.md
    └── <банк>/                      # подключённые банки: тот же вид
        ├── README.md
        └── topics/
```

🔑 **Деление здесь не «наше / общее», а «едет ли знание с проектом».**
Журнал проекта (`MEMORY.md`, `tasks/`, `diary/`, представления) привязан к этому проекту и
никуда не отчуждается; банки — знание, которое можно отдать и применить в другом месте.
⟹ вопроса «класть в свою память или в общую» нет, есть routing «**в какой банк**».

🔑 **Банк `local` есть всегда и называется так в любой установке.** Он отвечает на вопрос
«куда класть привязанное к месту, проекту или клиенту». Прочие банки подключаются
репозиториями и ничем от него не отличаются по устройству.

🔑 **Задача, её ход и её артефакты лежат в одном месте.** `backlog.md` и `archive.md` —
не хранилища, а **представления**, собранные из фронтматтеров `task.md` (см. ниже).

🚀 Читать всё это при старте руками не нужно: стартер `scripts/yamem-start.py` (лежит в каталоге
этого навыка) отдаёт готовый дайджест за один раунд (см. «При старте»).

## Канонические шаблоны

Используй эти шаблоны как основной формат. Если файлы уже существуют в похожем виде, сохраняй совместимость и не переписывай их без необходимости.

### `MEMORY.md`

Рекомендуемая структура:

```markdown
# Memory Index

Последняя оптимизация: YYYY-MM-DD

## Проект

- Краткое описание проекта
- Основные каталоги и точки входа

## Инфраструктура

- Среды, хосты, сервисы без секретов
- Где искать доступы и переменные

## Ограничения

- Что нельзя ломать
- Важные технические и организационные ограничения

## Факты

- Устойчивые факты о проекте

## Грабли и уроки

- ⚠️ Проблема и проверенное решение

## Ссылки

- Относительные ссылки на важные topics, tasks и документы
```

Правила:

- в `MEMORY.md` храни только устойчивые факты, ограничения и уроки;
- временные заметки и сырые наблюдения туда не пиши;
- записи должны быть короткими, проверяемыми и годными для повторного чтения через недели.

### Задача = папка (`tasks/YYYY-MM/<slug>/task.md`)

**Одна задача — одна папка.** Папка заводится **сразу**, как только задача появилась, даже если
в ней пока только `task.md`: конвенция «заведём папку, когда появится артефакт» ветвится и на
практике разваливается — часть задач остаётся строчками, связь «задача ↔ материалы» рвётся.

```markdown
---
title: Перевести шлюз домена на OpenWrt
client: Иванов
author: Роман
created: 2026-08-16
updated: 2026-08-16
urgent: false
important: true
status: in-progress
---

Kerio на шлюзе домена снимается с поддержки — заменить на OpenWrt, правила и
проброшенные порты перенести один в один, внешний IP не менять.

**Готово, когда:** трафик домена идёт через новый шлюз, старая VM выключена
с `onboot=0` как откат, проверены доступ наружу, VPN и входящие пробросы.
```

**Поля фронтматтера:**

| поле        | значение                                                                 |
| ----------- | ------------------------------------------------------------------------ |
| `title`     | одна строка, суть задачи; заголовка `#` в теле не нужно                   |
| `client`    | кому/за какую площадку делается (клиент, домен, «личное»)                 |
| `author`    | кто поставил задачу                                                       |
| `created`   | `YYYY-MM-DD`, дата появления задачи                                       |
| `updated`   | `YYYY-MM-DD`, дата последнего заметного движения                          |
| `urgent`    | `true`/`false` — горит ли срок                                            |
| `important` | `true`/`false` — влияет ли на результат                                   |
| `status`    | `new` / `in-progress` / `waiting` / `done`                                |
| `area`      | направление работ («Железо», «1С», «Мониторинг») — ось, поперечная клиенту |
| `epic`      | имя папки задачи-**темы**, в которую входит эта — см. «Темы (зонтики)»     |

- Обязательны `title`, `created`, `updated`, `status`; остальные — если известны.
- `urgent`/`important` — матрица Эйзенхауэра: по ним представление раскладывает задачи по
  приоритету, а `urgent: false` + `important: false` = «идея, кандидат без обязательства».
- Отдельного поля «дата завершения» нет: у `status: done` это `updated`.
- `waiting` — ждём внешнего действия; **чего именно ждём, писать в теле**, иначе статус бесполезен.
- Прочие ключи — легальные расширения, незнакомые не удалять.

**Что пишем в теле `task.md`: только «что сделать» и «когда готово».** 2–5 строк.
🎯 Формат обязан физически не давать писать сюда хронику — иначе задача превращается в журнал
(в прежнем бэклоге доходило до 11 тысяч символов на пункт, буквально журнал за четыре дня внутри
пункта). Разделение труда:

| куда                         | что туда пишем                                                        |
| ---------------------------- | --------------------------------------------------------------------- |
| `tasks/<месяц>/<slug>/task.md`    | **что сделать** и **критерий готовности**; постановка, а не отчёт     |
| `tasks/<месяц>/<slug>/journal.md` | **ход работ по этой задаче**: что пробовали, что не вышло, замеры     |
| `diary/<месяц>/<день>.<sid>.md`   | **что случилось за день** — по всем задачам сессии, коротко           |
| `topics/<topic>.md`               | устойчивое знание, добытое по ходу: рецепт, грабля, решение           |

⚠️ Разросшийся `task.md` — это не «подробная задача», а признак, что хроника легла не туда.

**Путь — `tasks/<месяц заведения>/<slug>/`**, месяц берётся из `created`: `tasks/2026-07/gateway-openwrt/`.
🔑 Раскладка именно по `created`, а не по статусу или дате закрытия: `created` не меняется никогда
⟹ путь задачи стабилен, перекладывать папку при закрытии не нужно и ссылки не протухают.

**Имя папки — slug без даты**, латиницей, `kebab-case`, по сути задачи: `gateway-openwrt`,
а не `2026-07-31-gateway-openwrt`. Дата уже есть в имени месяца и в `created`; внутри имени она
вдобавок врёт на длинных задачах (заведено в июле, делается в сентябре).
⚠️ Уже существующие папки с датой в имени **не переименовывать** — ссылки на них живут в топиках,
дневниках и коммитах; правило действует для новых.

**Ссылка на задачу** — на папку: `[gateway-openwrt](tasks/2026-07/gateway-openwrt/)`.

### Темы (зонтики): поле `epic`

🎯 **Задача, которую просят «продолжить» словом, а не путём, должна находиться за один шаг.**
«Продолжаем работу над ЭДО» упирается в то, что задач со словом ЭДО в памяти два десятка,
и по заголовкам они не различаются: агент видит при старте названия, а не содержание.

**Тема — обычная задача, на которую сослались другие.** Отдельного поля «я зонтик» нет:
зонтик тот, кого назвали в чужом `epic`. Подзадача пишет **имя папки темы, без месяца**:

```yaml
epic: perehod-na-platformu-edo-zapusk-v-boy
```

- 🔑 **Связь держит подзадача, а не тема.** Рукописный список внутри темы отстаёт всегда —
  проверено на живой памяти: в теле зонтика ЭДО значились 3 «отпочковавшихся» при 17 фактических.
  Список темы собирает генератор, руками его не ведут.
- Месяц в ссылке не нужен: имена папок задач по памяти уникальны (552 задачи, дублей нет),
  а месяц темы пришлось бы помнить и он ничего не уточняет.
- **Вложенность ровно в один уровень.** Тема с собственным `epic` — дефект, `--check` его ловит.
  Дерево тем даёт ту же навигацию, но добавляет обход и циклы, а разбирать их придётся посреди
  рабочей задачи.
- Закрытие темы при открытых подзадачах — тоже жалоба `--check`: так тема не исчезает из вида
  вместе с незакрытой работой.

**Три сценария:**

| когда                | что делает агент                                                             |
| -------------------- | ---------------------------------------------------------------------------- |
| завёл задачу         | тема по смыслу уже есть (их список печатает стартер) — ставит `epic`; нет — обычная задача |
| «продолжаем <тема>»  | берёт тему из блока «☂ Темы», читает её `prompt-next-session.md`, оттуда — в подзадачу |
| закрыл подзадачу     | `status: done`, и всё: список темы пересобирается сам                        |

⭐ Побочный эффект, ради которого это стоит делать даже при одной теме: **дайджест перестаёт
разбухать**. Два десятка строк одной темы сворачиваются в одну, а сами задачи остаются
доступны целиком — полный список едет отдельными частями стартера.

### Промпт продолжения — `prompt-next-session.md`

⭐🔑 **ПРАВИЛО: у задачи, которая переживает сессию, обязателен `prompt-next-session.md`
в её папке.** Пишется перед завершением работы, если задача не закрыта, и обновляется, а не
дописывается: это снимок состояния, а не журнал (журнал — `journal.md` рядом).

Что в нём: контур, который не надо переоткрывать (адреса, версии, где что лежит), что сделано,
что открыто, чем продолжать. 🎯 Мотив: без него «продолжаем X» стоит разведки заново — а она
уже сделана и лежит в памяти.

⚠️ **Имя файла ровно такое.** В памяти уже есть промпты под пятью разными именами
(`next-session-prompt.md`, `prompt-<дата>.md`, `onboarding-prompt.md`…) — стартер их распознаёт,
чтобы ничего не потерялось, но новые заводить только каноническим именем.

Стартер печатает у каждой темы `📝 промпт <дата>` либо `⚠️ промпта нет` — второе означает,
что продолжать придётся разведкой.

### `backlog.md` и `archive.md` — генерируемые представления

⚙️ **Оба файла собираются из фронтматтеров `task.md` — руками их не правят.**
`backlog.md` показывает всё, что не `done`, `archive.md` — завершённое по месяцам.

- 🔑 **Источник данных для агента — сами задачи**, а не эти файлы. Они остаются в git ради
  чтения человеком, обзора с GitHub и как фолбэк, если генератор не запускался.
- «Завершить задачу» = `status: done` в её `task.md`. Ручного переноса текста между файлами
  больше нет — именно он раньше и не делался, отчего закрытые задачи висели в бэклоге.
- Правка, сделанная прямо в `backlog.md`, потеряется при следующей сборке. Заметил расхождение —
  чини `task.md` и пересобирай.

**Сборка** — тем же каталогом скриптов, что и стартер (`<навык>/scripts/`, см. «При старте»):

```bash
python <навык>/scripts/gen-backlog.py --memory <путь к .agents/memory> --apply
```

- Без `--apply` — сухой прогон: показывает, что изменится, и ничего не пишет.
- `--check` даёт ненулевой код, если представление разошлось с задачами или во фронтматтерах
  есть дефекты (нет обязательного поля, статус вне набора, `updated` раньше `created`,
  папка задачи без `task.md`, а также битая форма фронтматтера — та же строгая проверка,
  что у индекса топиков: `title: sts-ac: учёт материалов` без кавычек ломает YAML). ⚙️ Ставится в pre-commit памяти —
  `scripts/yamem-precommit.sh` проверяет заодно и индекс топиков; без этого представление
  устаревает молча, а в git выглядит живым.
  ⏱ Готовый глобальный хук — `template/git-pre-commit.sh`: он же гоняет gitleaks. 🔑 Две
  вещи в нём сделаны ради старта сессии, и обе оплачены замером: коммит **только** отметки
  на доске пропускает проверку представлений (там проверять нечего), а найденный путь
  к скрипту кешируется в `git config --global yamem.precommit` — перебор кандидатов
  с globом по `~/repo/*` стоит ~0.75 с на NTFS. Отметка на доске: **4.5 → 1.2 с**.
- Скрипт правит только текст между маркерами `<!-- yamem:backlog:begin/end -->` и
  `<!-- yamem:archive:begin/end -->`; шапка файла и всё вне маркеров остаются как есть.
- Разложение по секциям: `in-progress` → «В работе», `waiting` → «Ожидает», остальные —
  по квадрантам `urgent`/`important`. Архив группируется по месяцу закрытия.
- ⚠️ Представление пересобирается целиком ⟹ собирать **после `git pull --rebase`**, иначе
  своей сборкой откатишь задачи соседней сессии.

### Фронтматтер топика (`topics/<topic>.md`)

Каждый топик начинается с YAML-фронтматтера (формат [OKF](https://github.com/GoogleCloudPlatform/knowledge-catalog)):

```markdown
---
type: recipe
description: Одно предложение про то, когда сюда возвращаться.
---

# Название темы
```

- **Обязателен только `type`.** Значения — по **форме** документа, а не по предмету (предмет уже
  закодирован банком и именем файла), потому что форма говорит, КАК документ применять:
  - `recipe` — как сделать; исполняют по шагам;
  - `reference` — справка, инвентарь, срез состояния; смотрят;
  - `incident` — разбор случая; читают как прецедент;
  - `rule` — договорённость, принятое решение; подчиняются.

  Топик-солянка из двух форм — повод его расщепить, а не изобретать пятое значение.
- **`description` — условие обращения, одно предложение**: по какому запросу и в какой ситуации
  этот файл нужно открыть. ⚠️ **Не пересказ содержания** — из «здесь про Samba AD, DNS и репликацию»
  нельзя решить, читать или нет; из «когда DC не отдаёт шару, разъехалась репликация или не
  проходят динамические DNS-апдейты» — можно. Та же ошибка, что в `description` навыка.
- Прочие ключи (`title`, `tags`, `keywords`, `updated`) — легальные расширения, по желанию;
  незнакомые ключи не удалять.
- 🔑 **Трогаешь топик — дописываешь фронтматтер, если его нет.** Новый топик заводится сразу с ним.
- Раздел «База знаний» в `MEMORY.md` и списки топиков в README банков **генерируются из
  `description`** — руками там строки не вести (рукописный индекс расходится с правдой и
  оплачивается каждой сессией). Сборка — `python <навык>/scripts/gen-topics-index.py --memory
  <путь к .agents/memory> --apply`; она подставляет список между маркерами
  `<!-- yamem:topics-index:begin/end -->`, всё вне маркеров не трогает. Флаг `--check` даёт
  ненулевой код, если индекс разошёлся с топиками либо у топика **битый фронтматтер**:
  нет `type`, `type` вне набора четырёх значений, нет `description`, а также структурные
  дефекты формы — двоеточие в значении без кавычек, BOM, незакрытый `---`.
  ⚠️🔴 **Проверка формы строгая, а чтение — толерантное, и это намеренно**: генератор обязан
  собраться и на кривом файле, иначе одна опечатка гасит весь индекс. Отсюда прежняя дыра:
  `description: Когда нужно X: делай Y` без кавычек собирался зелёным, а `yaml.safe_load`
  на том же файле падал — то есть файл был сломан для всех, кроме нас (вскрыто 20.08 на двух
  топиках банка `lion`, а в задачах памяти нашлось ещё 15 таких же).
  Судит настоящий YAML-парсер, если PyYAML в среде есть; на голом python те же дефекты
  ловятся эвристиками — жёсткой зависимости у скриптов нет по-прежнему.
  Вкусовые замечания (слишком короткий `description`) печатаются, но код возврата не портят:
  pre-commit не должен вставать из-за формулировки.

## Правила

### При старте

🚀 **Весь preflight — два раунда: загрузка этого навыка и один блок вызовов стартера.**

⚠️ Меньше двух не бывает и обещать не нужно: путь к скриптам приезжает вместе с навыком,
так что первый раунд — сам `Skill`, второй — все части стартера сразу.

🔑 Скрипты лежат **рядом с этим файлом** — в каталоге `scripts/` того самого каталога навыка,
что выдан тебе строкой «Base directory for this skill» при загрузке. Искать их где-то ещё
не нужно: подставь этот базовый каталог вместо `<навык>` ниже.

```bash
python <навык>/scripts/yamem-start.py --memory <путь к .agents/memory> --sid <первые 8 символов id сессии> --topic "<чем занимаешься>" --part 1
python <навык>/scripts/yamem-start.py --memory <путь к .agents/memory> --sid <первые 8 символов id сессии> --part 2
...
python <навык>/scripts/yamem-start.py --memory <путь к .agents/memory> --sid <первые 8 символов id сессии> --part 24
```

⚠️ **Все вызовы — в одном сообщении, параллельно, и зови с ЗАПАСОМ — 24 части.**
🔑 Ошибка тут несимметрична: лишняя часть возвращает `(пусто)` за 0.15 с, а недобор стоит
**целого раунда** латентности (12–23 с), потому что точное `N` печатает часть 1 — то есть
становится известно уже после того, как ты решил, сколько звать. Поэтому берём заведомо больше:
фактическое число плавает с объёмом памяти (на 21.08 — 19: ядро, обстановка,
4 части задач, 6 частей `MEMORY.md`, 7 частей дневников за 7 дней).

Дайджест целиком длиннее лимита вывода инструмента (~30 КБ): при печати одним куском харнес
молча подменяет его превью, и данные до тебя не доезжают. Параллельные вызовы стоят
**один раунд** латентности, но приносят весь объём.

Что в частях:

| часть | что                                                                                  |
| ----- | ------------------------------------------------------------------------------------ |
| 1 — ядро | синхронизация, **активные соседи одной строкой**, счётчики задач, **сроки из тел задач**, **темы**, раскладка остальных частей |
| обстановка | доска сессий за сутки с их результатами, банки топиков, коммиты памяти за сутки  |
| задачи   | полный список открытых задач по секциям — **не усечён**                            |
| MEMORY.md | весь файл целиком — отдельно читать не нужно                                      |
| дневники | сводки за `diary_read_days` дней                                                    |

🔑 **Ядро намеренно маленькое и стабильное** (~5 КБ против прежних 27.5 при потолке 28):
это единственная часть, которую нельзя нарезать, поэтому списки в ней не живут. Замер 21.08
показал, что 78 % её веса давали три растущих блока — сессии (34 %), банки (22 %), коммиты
(22 %); они уехали в «обстановку». ⚠️ Что где лежит — не про важность: части приезжают
**одним раундом** и читаются все, так что на полноту картины раскладка не влияет.

🔑 **Список задач больше НЕ усекается.** Раньше ядро подбирало, сколько задач «в работе»
влезает в потолок вывода, и остаток пропадал совсем: задача из хвоста была невидима сессии,
пока та не откроет `backlog.md` руками — то есть лишним раундом, которого никто не делал.
Теперь ядро показывает свежие, а полный список едет своими частями. ⟹ `backlog.md` отдельно
читать не нужно **никогда**: он для человека и как фолбэк.

⚙️ **Стартер сам проверяет, не отстал ли навык от своего origin** — `fetch` едет тем же
параллельным блоком, что и pull банков, поэтому лишнего раунда нет. 🔑 Пак подключён
git-субмодулем и junction'ами, а не маркетплейсом ⟹ обновление — это `git pull` в его
каталоге, а НЕ `claude plugin update` (тот к субмодулю неприменим).
⚠️ Стартер только сообщает и не обновляет сам: SKILL.md к этому моменту уже прочитан,
а скрипты сменились бы под ногами между частями дайджеста — часть собралась бы старым
кодом, часть новым. Обновляться — между сессиями.

⚠️ **Счётчик «в работе без движения»** в блоке задач: `in-progress`, у которых `updated`
старше недели и двух. 🎯 Это не украшение — на 21.08 из 57 задач «в работе» живых за
три дня было **19**, а протухших больше недели **30**. Протухший статус неотличим от
работы и занимает место в каждом дайджесте, пока его не разобрать. Увидел большой
счётчик — предложи оператору разбор, не жди плановой оптимизации.

📅 **Сегодняшнюю дату бери из шапки части 1**, а не из своих представлений о ней: стартер
печатает её первой строкой именно для этого. Неверная дата в записи памяти тиражируется —
её потом читают все следующие сессии (прецедент 17.08: запись ушла в память как 18.08).
🔑 **`MEMORY.md` отдельно читать не нужно** — он приезжает этими же частями. Читать его
`Read`-ом означает 3 лишних раунда: 90 КБ ≈ 33К токенов не влезают в один вызов.

🔑 **Каждая часть заканчивается строкой `— конец части K/N —`.** Это твоя проверка:
- строки нет ⟹ вывод обрезан харнесом, дочитай сохранённый файл;
- `N` больше числа вызванных частей ⟹ дозови недостающие, тоже одним блоком;
- лишняя часть вернёт `(пусто)` — это нормально, дневников просто меньше.

⚠️ Побочные действия (pull банков, отметка на доске, `--prune`) делает **только часть 1** —
поэтому `--topic` и `--prune` имеют смысл лишь при ней, а параллельные части не дерутся
за git-индекс.

Стартер делает всё, что раньше было списком из одиннадцати шагов и потому регулярно
выполнялось наполовину: синхронизирует банки (`git pull --rebase`), пишет твою отметку на доске
сессий, показывает **сессии за сутки вместе с их результатом**, собирает дайджест задач
(в работе / ждут / срочные — строкой, остальное счётчиками), имена топиков по банкам с пометкой
одноимённых пар, остаток коммитов памяти за сутки, сводки дневников за `diary_read_days` дней
и напоминание про оптимизацию.

🔑 **Блок «Сессии за сутки» читать как ответ на два вопроса сразу:**
- 🔵 — сосед в работе прямо сейчас, под ним `↳` его последние коммиты в память ⟹ **что он уже
  успел**, а не только за что взялся. Его задачи не бери.
- ⚪/⚫ — сессия закончила работу в пределах суток (⚫ — её запись снята). `↳` — с чем
  закончила. ⚠️ Рядом с sid — **сколько времени прошло с последней активности**, а не время
  суток: отметка пишется при старте, а строка живёт по последнему коммиту, и эти часы
  расходятся на сутки и больше.
- ⚠️ **без следа** — тему брали, а в памяти по ней пусто. 🎯 Именно так 17.08 один и тот же
  утренний обзор «что горит» сделали **трижды**: доска показывала тему и молчала о результате.
  Увидел свою тему в этом списке — сначала посмотри дневник и коммиты той сессии, потом решай,
  делать ли заново. «Без следа» ≠ «не сделано»: работа могла не доехать до памяти.

⚙️ **Брошенные записи снимаются сами** (старше 26 ч) — тем же коммитом, что и твоя отметка,
руками `--prune` звать не нужно. Порогов два намеренно: 6 ч — «уже не активна» (в списке
остаётся), 26 ч — «снять с доски». Один порог сносил бы запись сессии, которая работает восьмой
час: отметка пишется при старте и смене темы, а не по таймеру. Живость считается по ФАКТУ —
свежая отметка **или** свежий коммит с дневником этой сессии.

Полезные ключи: `--diary heads|red|marks|full` (подробность сводок, по умолчанию `red` —
заголовки дня плюс строки с 🔴), `--prune` (снять неактивные записи сразу, порог 6 ч), `--no-sync`,
`--part-limit` (потолок части в **байтах** utf-8, по умолчанию 20000). Без `--part` печатается
всё одним выводом — годится для запуска руками в терминале, но не для вызова из сессии.

**После стартера:**

1. Ничего дочитывать «для полноты картины» не надо: ядро, `MEMORY.md` и сводки дневников уже
   пришли частями. ⚠️ Лишний `Read` — это не просто файл, это **раунд латентности**
   (12–23 с каждый), и на них уходит львиная доля времени старта.
2. Дочитывай **только то, без чего не ответить на заданный вопрос**: `task.md` задачи, о которой
   спрашивают, дневник дня целиком, если сводки не хватило, топик по теме запроса. Это уже
   не preflight, а работа — и она законна.
3. В первом ответе кратко назови: статус синхронизации, **активные соседние сессии и их темы**
   (или «других сессий нет»), срочные и незакрытые задачи. Если твоя тема уже встречается
   в списке сессий за сутки — скажи об этом сразу, до того как начнёшь её делать второй раз.
4. Если стартер сообщил, что оптимизация памяти просрочена — предложи её, но **файлы не меняй
   без подтверждения**.

⚠️ **Если стартера нет** (yamem подключён без скриптов) — тот же preflight руками:
прочитать `yamem.config.yaml`; синхронизировать репозиторий памяти и банки, не блокируясь на
ошибке; прочитать `MEMORY.md` и фронтматтеры `tasks/*/*/task.md` (тела и `done` — не надо,
готовое представление всего этого — `backlog.md`); прочитать дневники за `diary_read_days` дней
по маске `diary/YYYY-MM/YYYY-MM-DD*.md`; записать свою отметку в `.sessions/<sid>.md` и прочитать
чужие (свежее 6 часов = активные); получить имена топиков всех банков, отметив одноимённые.

⚠️ Если памяти нет вовсе — создай минимальную структуру: `MEMORY.md` по шаблону, `diary/`,
`tasks/`, `banks/local/topics/`. `backlog.md` и `archive.md` руками не создавай, их соберёт
генератор представлений.

🔑 **И положи правило preflight в `CLAUDE.md` самого проекта** — готовый блок лежит в
`template/CLAUDE.snippet.md` этого навыка (если `CLAUDE.md` уже есть — дописать в конец,
не перезаписывать). Правило живёт рядом с памятью, а не в глобальном `~/.claude/CLAUDE.md`:
безусловное «вызови yamem» срабатывает и в проектах, где ни памяти, ни навыка нет.

### При работе над задачей

1. Задача взята в работу — **заведи или найди её папку** `tasks/<месяц created>/<slug>/`
   и поставь в `task.md` `status: in-progress` + свежий `updated`. Ход работ пиши в
   `journal.md` рядом, артефакты клади туда же (см. «Задача = папка»).
2. **Обязательно перед содержательным действием** проверь накопленное знание по теме запроса:
   - сопоставь ключевые слова запроса с именами файлов из `topics/` и `tasks/` **всех банков**,
     полученными при старте;
   - если совпадение есть (точное или близкое по смыслу) — прочитай файл целиком ДО первого действия, не действуй вслепую;
   - 🔑 **если имя нашлось больше чем в одном банке — читать ВСЕ найденные, а не первый попавшийся**
     (см. следующий раздел);
   - проверь `MEMORY.md`, задачи в `tasks/` и недавний diary на упоминания темы;
   - если по именам не нашлось — используй текстовый поиск (`rg`, `grep` или эквивалент) по содержимому `banks/*/topics/`, `tasks/` и `MEMORY.md`.
3. Если найдены предупреждения, ограничения или грабли, учитывай их при планировании.

### Одноимённые топики в разных банках

🔑 **Одинаковое имя файла в двух банках `banks/` — это НЕ дубль и НЕ выбор, а одна тема,
намеренно разложенная по слоям.** Общий банк держит универсальную часть (рецепт, годный на чужом
стенде), `local` — специфику этого места. Ни один из них не полон сам по себе.

**Чтение — компиляцией, а не выбором:**

1. топик общего банка даёт **базу**: как это устроено и как делать;
2. топик `local` даёт **дельту**: что развёрнуто у нас, какие адреса/параметры, какие решения
   приняты и почему, чем наш случай отличается от рецепта;
3. итог = база + дельта. ⚠️ Читать только `local` — потерять процедуру и грабли; читать только
   общий — действовать по чужим умолчаниям на нашем стенде.

⚠️ Одноимённых банков может быть и больше двух — читать **все**, а не первые попавшиеся два.
Стартер помечает такие имена при старте.

⚠️ **Прямое противоречие между банками по универсальной технике — это не «local главнее», а
сигнал, что один из них протух.** Проверить фактом и починить оба, а не молча выбрать удобный.

**Запись — по тому же разделу:**

- воспроизводимое у других (процедура, грабли платформы, конфиг-шаблоны с плейсхолдерами) → общий банк;
- наши хосты, адреса, VMID, решения и их мотив, прецеденты, указатели на секреты → `local`;
- если тема уже есть в общем банке, а новое знание универсально — дописывать **туда**, а не
  заводить дубль в `local`;
- в топике `local` на пару ссылаться **по имени** («универсальная часть — общий топик `имя`»), не
  относительным путём: путь протухнет при первом переносе банка.

⚠️ **Историзм не хранить ни в одном из слоёв** — история изменений уже есть в git, а топик
перечитывается каждую сессию. Единственное исключение — **опровержение живучего заблуждения**
(ошибки, к которой интуиция возвращается сама): его оставляют как знание. Признак: сделает ли тот же
неверный вывод следующий читатель. Разовую описку просто исправляют, не упоминая, что было не так.

### Перед ответом

Если в ходе работы появился устойчивый полезный результат, обнови память.

Под устойчивым полезным результатом понимаются:

- новый факт о проекте;
- новое ограничение или грабля;
- новое решение, рецепт или урок;
- новая задача;
- завершение или изменение статуса задачи;
- полезный артефакт по отдельной задаче.

Если работа была короткой, ознакомительной или не оставила полезного следа, память не обновляй.

При обновлении памяти:

1. Добавь краткую запись в дневник текущего дня:
   - `diary/YYYY-MM/YYYY-MM-DD.<sid>.md` — **свой** файл дня, см. «Параллельные сессии»
   - 📅 дату бери из шапки стартера, а не по памяти: ошибка здесь создаёт файл-двойник
     на несуществующий день и разъезжается со ссылками
2. Обнови задачи:
   - новая задача — заведи папку `tasks/<месяц>/<slug>/` с `task.md` (фронтматтер + что сделать
     + критерий готовности); ⚙️ если она продолжает уже идущую **тему** — поставь `epic`
     (список тем печатает стартер, см. «Темы (зонтики)»);
   - движение по существующей — поправь `status` и `updated` в её `task.md`, ход работ
     допиши в `journal.md` той же папки;
   - ⭐🔑 **работа не закончена, а сессия заканчивается** — обнови (или заведи)
     `prompt-next-session.md` в папке задачи: контур, что сделано, что открыто, чем продолжать.
     🎯 Это единственное, что отличает «продолжаем X» за одно чтение от разведки заново;
   - завершена — `status: done`; переносить текст никуда не надо;
   - ждём внешнего действия — `status: waiting` и **чего именно ждём** в теле задачи;
   - ⚙️ пересобери представления `backlog.md`/`archive.md` (см. «генерируемые представления»)
     — руками их не правь
3. Общие и устойчивые факты добавь в `MEMORY.md`
4. Тематические знания и повторяемые решения добавь в `banks/<банк>/topics/<topic>.md`.
   🔑 Сначала реши, **в какой банк**: привязанное к месту, проекту или клиенту — в `local`,
   отчуждаемое — в банк по его оси (ремесло, площадка, роль).
   ⚠️🔴 **Отдельно проверь себя, когда дописываешь в УЖЕ открытый топик `local`.** На этой ветке
   решение «в какой банк» заново не принимается, и универсальное знание оседает там, где просто
   дешевле дописать: файл уже открыт, раздел по теме уже есть, append стоит одну команду, а
   расщепление — имя, фронтматтер, коммит в субмодуль и пересборка индекса. Две проверки перед `>>`:
   - **переживёт ли строка неделю?** Счётчики и списки текущего состояния («активных 9»,
     «выключены такие-то») — это ответ на сегодняшний вопрос, а не знание: топик перечитывается
     каждой сессией и подаёт их как правду ⟹ состояние живёт в задаче и дневнике, в топик идёт
     механика, по которой его добывают;
   - **вынимаются ли имена проекта подстановкой?** Вынимаются — абзац универсальный, его место
     в банке по ремеслу, а в `local` остаётся дельта и ссылка на общий топик по имени.
   ⚠️ Проверь, нет ли топика с этим именем в другом банке — если есть, универсальная часть
   пишется туда, а в `local` остаётся только дельта (см. «Одноимённые топики в разных банках»).
   ⚠️ Новый топик заводи сразу с фронтматтером; у тронутого — допиши, если его нет
   (см. «Фронтматтер топика»)
5. В общий банк материал попадает, только если он:
   - обезличен;
   - полезен вне текущего проекта;
   - не содержит чувствительных данных;
   - достаточно стабилен, чтобы считаться рецептом, а не сырым журналом

   ⭐ Признак кандидата: **в топике почти нет имён этого проекта**. Тогда правильный ход — не
   «перенести целиком», а **расщепить**: универсальное уезжает в общий банк, в `local` остаётся
   дельта и ссылка на общий топик по имени

### Параллельные сессии (обязательно)

Над одной памятью могут одновременно работать несколько сессий — в разных окнах, на разных
машинах, в фоне. `MEMORY.md`, топики и собираемые представления — общие, и **чужая запись может
появиться между твоим чтением и твоей записью**. Полная перезапись такого файла молча уничтожает
чужую работу, причём проверка «мой текст на месте» этого НЕ ловит: свои строки как раз сохраняются.

#### Идентификатор сессии `<sid>`

Возьми первые 8 символов идентификатора текущей сессии (он есть в пути рабочего каталога для
временных файлов, выданного тебе средой). Он стабилен на всю сессию и уникален. Пример: `3c7937e2`.

#### 1. Свой файл дня (устраняет затирание, а не смягчает его)

Пиши **не** в общий файл дня, а в **свой** `diary/YYYY-MM/YYYY-MM-DD.<sid>.md`. Первой строкой —
человекочитаемый заголовок: `# 2026-08-10 — обход мониторинга (3c7937e2)`.

Тогда две сессии физически не могут перезаписать работу друг друга: у каждой свой файл.
Чтение при старте — по маске `diary/YYYY-MM/YYYY-MM-DD*.md` (см. блок «При старте»). Склейку файлов
одного дня в один делай при оптимизации памяти, а не по ходу работы.

⚠️ Существующий общий файл дня `diary/YYYY-MM/YYYY-MM-DD.md` за уже начатый день не переименовывай и не трогай —
просто заведи рядом свой и пиши в него.

#### 2. Доска активных сессий

`.sessions/<sid>.md` — четыре поля, обновляется при старте и при смене темы:

```markdown
started: 2026-08-10 09:05
updated: 2026-08-10 11:25
topic: обход Zabbix, чистка шума мониторинга
hosts: zabbix.ag, srv-rds1.ag
```

Смысл: до того как взять задачу, посмотри, не ведёт ли её соседняя сессия. Это же снимает ложную
тревогу «кто-то посторонний правит боевые хосты» — **по логам самих хостов агентов не отличить**,
если они ходят с одной машины под одной учёткой и одним ключом.

🔑 **Поля «результат» здесь намеренно нет.** Чем сессия закончила, стартер берёт из её коммитов
в память: дневник называется `diary/<месяц>/<дата>.<sid>.md` ⟹ связь «коммит → сессия» уже есть,
и она не требует дисциплины что-то дописывать. Ровно те три сессии, что 17.08 продублировали
утренний обзор, не оставили и строки в дневнике — поле результата они бы тоже не заполнили.
⟹ **пиши в дневник своего дня — это и есть отметка результата** для соседей.
⚙️ Свой файл на доске удалять при выходе не надо: брошенное снимается автоматически (см. выше).

#### 3. Правила записи в общие файлы (`MEMORY.md`, `topics/`, представления)

⭐ Задача — **отдельный файл** `tasks/<месяц>/<slug>/task.md`, поэтому две сессии, ведущие разные задачи,
друг другу больше не мешают. Опасность остаётся у файлов, которые пишут все сразу: `MEMORY.md`,
топики и **генерируемые** `backlog.md`/`archive.md`. ⚠️ Представление пересобирается целиком
⟹ собирать его **после `git pull --rebase`**, иначе своей сборкой откатишь чужие задачи.

1. **Дописывай в конец добавлением (`>>`), а не перезаписью файла целиком.**
   Инструмент, который переписывает файл (Write), для общих файлов памяти не годится — только
   append либо точечная правка конкретного фрагмента (Edit).
2. **Перед записью — `git pull --rebase`**, после записи — сразу `git add` + `commit` + `push`.
   Чем меньше окно между чтением и коммитом, тем меньше шанс расхождения.
3. **Коммить сразу после своего блока**, не копи изменения до конца сессии.
4. **`git add` перечисляй по файлам, а не `git add -A`** — иначе в твой коммит попадут чужие
   незакоммиченные правки. Если `-A` всё же использован, сообщение коммита должно описывать твои
   изменения, а не притворяться, что все изменения твои.
5. Если после своей записи видишь, что файл потерял чужие разделы — **восстанови слиянием**:
   `git show <предыдущий_коммит>:<путь>` даёт прежнюю версию, из неё возвращаются пропавшие
   разделы, затем дописывается своё. Не «переписать поверх ещё раз».
6. Правка задачи — точечная правка её `task.md` (статус, дата, пара строк), а не перезапись
   файла целиком; `backlog.md`/`archive.md` не трогать вовсе, они собираются.
7. 🔑 **Прежде чем взять задачу — посмотри `git log` памяти за сегодня** (`git log --since=…
   --oneline`) и доску `.sessions/`. Соседняя сессия могла уже закрыть её час назад: сообщения
   коммитов это показывают сразу, и это дешевле, чем обнаружить дубль после часа работы.

⚠️ Признак, что тебя затёрли: в `git log` по файлу дня видно изменение с большим числом
удалённых строк (`186 ++--- 141 deletions`) от коммита соседней сессии.

### Git-правила

Если `local.commit_on_update=true`, коммить изменения памяти только при наличии реальных изменений.

Правила:

- не делай пустой commit;
- ошибки commit/push не должны блокировать основной ответ;
- если remote, upstream, авторизация или branch не настроены, просто сообщи об этом кратко;
- не переписывай историю памяти и не делай рискованных git-действий без явного запроса пользователя.

Для подключённых банков действуют те же правила.

### Безопасность

- Запрещено хранить в памяти:
  - пароли, токены, ключи, секреты;
  - персональные данные;
  - чувствительные данные клиентов;
  - внутренние URL, IP, хосты, логины;
  - любые данные, которые нельзя безопасно закоммитить в git.
- В журнале проекта и банке `local` храни только ссылку на место поиска секрета, имя переменной или безопасное описание.
- В общих банках правила ещё строже: только полностью обезличенные материалы. ⚠️ Отчуждаемый банк
  видят посторонние — утечка туда стоит дороже, чем в `local`.

### Поиск

- Если не уверен, где нужная информация, используй доступный в среде текстовый поиск (`rg`, `grep` или эквивалент) по журналу проекта и банкам.
- ⚠️ Поиск вести **сразу по всем банкам** (`banks/*/`), а не только по `local`: тема может быть описана в общем банке, а в `local` иметь лишь короткую дельту — или наоборот.

## Оптимизация памяти

⚙️ **Сам блок вынесен в отдельный файл `OPTIMIZATION.md` рядом с этим** — он нужен раз в
неделю, а `SKILL.md` грузится в каждой сессии у каждого участника. Здесь остаётся только
триггер и условие, при котором тот файл надо открыть.

Оптимизация запускается:

- по команде пользователя («оптимизируй память», «прибери память»);
- автоматически **только в режиме анализа**, если пришло время по конфигу.

🔑🔴 **Сработал триггер — ПЕРЕД первым действием прочитай `<навык>/OPTIMIZATION.md` целиком**
(`<навык>` — каталог, выданный строкой «Base directory for this skill»). По памяти не
действовать: там три фазы, список проверок и деление операций по **радиусу записи** — что можно
делать при живых соседних сессиях, а что только при пустой доске. Половина операций
переписывает общие файлы, и ошибка на этом стирает чужую работу молча.

⭐ Единственное, что нужно знать, не открывая файл: **фаза 1 (анализ) файлов не меняет и
безопасна при любом числе соседей** ⟹ предложить прогон можно всегда, даже если выполнение
придётся отложить целиком.

## Примеры

### Запись в дневник (diary/YYYY-MM/YYYY-MM-DD.<sid>.md)

```markdown
## Краткое название задачи

- Сделано: ...
- Грабля: ...
- Артефакт: [../../tasks/2026-03/dfs-fix/](../../tasks/2026-03/dfs-fix/)
```

### Новая задача (tasks/2026-03/dfs-fix/task.md)

```markdown

title: Починить DFS-namespace после вывода Windows DC
client: prodline
author: Роман
created: 2026-03-21
updated: 2026-03-21
urgent: true
important: true
status: new

После вывода старого DC часть клиентов не открывает `\\<домен>\storage` —
разобрать и починить, не задев рабочие junction.

**Готово, когда:** корень namespace открывается с любого клиента на обоих DC,
в логах нет `chdir_current_service ... Permission denied`.
```

```markdown
# Ход работ
```

### Когда заводить новый банк

Банк заводится не под структуру предметной области, а под **вторую сторону, которая будет в него
писать или читать**, и по **оси, по которой она это делает**. Осей на практике две, и они дают
разные банки:

- **ремесло** — знание, годное всем независимо от места («как работать с напарником», «как
  устроена 1С»). Такой банк общий, и пишут в него все;
- **площадка** — фактура конкретного места: имена и адреса машин, какие сервисы где, регламенты.

🔑 **Ось площадки задаётся не удобством, а границей доступа.** Если у площадок разные читатели —
одному видна одна, другому другая, — общий банк «на все площадки» не годится ни при каком составе:
разделить доступ внутри одного репозитория нечем. ⟹ банк на площадку, имя вида `<площадка>-site`.

⚠️ **Расщепить существующий банк переносом файлов, скорее всего, не выйдет** — и это стоит
измерить до того, как планировать работу. Замер на живой памяти (2026-08): из 70 топиков только
7 упоминали одну площадку, а **49 топиков и 81 % объёма — несколько сразу**. Тексты пишутся
по ходу работы, а работа идёт по нескольким площадкам в один день.

⟹ **Банк площадки собирается по сценарию, а не переезжает.** Критерий наполнения — вопрос
«что нужно знать, чтобы здесь работать», а материал вычитывается из смешанных топиков.
🎯 Побочный эффект, ради которого это и делается: сборка по сценарию отсекает журнал разработки.
В том же прогоне из 932 КБ исходного банка в банк площадки уехало 42 КБ — при том что ничего
нужного не потерялось.

⚠️ Что в банк площадки **не кладут**: учётные записи, пароли, пути к чужим ключам. Читатель
прописывает свои — в инвентаре только адреса и роли. Сведения о людях — отдельное решение
владельца, по умолчанию их там нет.

### Подключение банка

Банк — обычный каталог с `README.md` и `topics/`. Отчуждаемый банк удобно держать отдельным
репозиторием и подключать субмодулем:

```bash
git submodule add <url> .agents/memory/banks/<имя>
```

После этого банк добавляется в `banks:` конфига — иначе скрипты и стартер его не увидят:

```yaml
banks:
  - name: <имя>
    path: banks/<имя>
    type: submodule
    pull_on_start: true
```

### Вынос памяти в отдельный репозиторий

Память целиком (`.agents/memory`) — кандидат в субмодуль: журнал проекта приватен, а проект
рядом может быть публичным. Сначала перенеси содержимое в репозиторий памяти, только потом
подключай:

```bash
git submodule add <url> .agents/memory
```

⚠️ Банки-субмодули внутри становятся **вложенными** субмодулями репозитория памяти, а не проекта.
